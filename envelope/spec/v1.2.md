# Anchored Receipts — Envelope v1.2

**Status:** Spec. Approved 2026-05-17.
**License (spec):** CC0
**License (reference implementation):** Apache 2.0
**Package:** `@dekimuhq/anchors-envelope`

This document is the in-tree, package-shipped mirror of the canonical v1.2 spec. It snapshots the four envelope additions and the JSON Logic operator allowlist for downstream verifier authors building outside the reference TS impl.

The canonical (versioned) source lives in [`dekimuhq/anchors-spec`](https://github.com/dekimuhq/anchors-spec/tree/main/envelope). Where this mirror and the canonical text disagree, the canonical text wins until the next package release.

---

## 1. Additive fields

v1.2 adds four optional envelope fields. v1.1 receipts remain byte-equal verifiable against v1.2 verifiers.

| Field | Type | Required? | Purpose |
|---|---|---|---|
| `kind` | `"observation" \| "decision" \| null` | Optional | Receipt classification — observation vs decision (Art. 22 evidence taxonomy). |
| `cause` | closed-enum string (see §2) | Optional | Typed trigger naming what caused the receipt to issue. |
| `predicate` | JSON Logic AST (operators restricted, see §3) | Optional | Verifiable condition committed to the receipt. |
| `iat_ms` | `number` | Optional in v1.1, **mandatory in v1.2** | Unix-ms mirror of `iat` (ISO 8601) — enables numeric predicate comparisons against issuance time. |

Field inventory grows 18 → 22. The four new fields are inside the RFC 8785 canonicalised signing input — they sit under the existing Ed25519 signature; no separate signing scope, no new cryptographic primitives.

## 2. `cause` closed enum

```
manual | scheduled | event | api | regulatory_request |
rectification | erasure_request | portability_request |
objection | automated_decision_review | null
```

Adding a value is purely additive (no envelope version bump). Removing or repurposing a value requires v1.3+.

## 3. JSON Logic operator allowlist

27 operators, exported as `JSON_LOGIC_ALLOWLIST_V1_2` from `@dekimuhq/anchors-envelope`. Operators outside the allowlist make the receipt invalid (error code `predicate_operator_not_allowed`).

| Group | Operators |
|---|---|
| Equality | `==`, `===`, `!=`, `!==` |
| Boolean | `!`, `!!`, `and`, `or` |
| Ordering | `>`, `>=`, `<` (2- or 3-ary between form), `<=` (2- or 3-ary between form) |
| Arithmetic | `+`, `-`, `*`, `/` (rejects div-by-zero), `%` (rejects mod-by-zero) |
| Conditional | `if` (chained form supported) |
| Set / membership | `in`, `all`, `none`, `some` (iteration-context shift per standard JSON Logic) |
| Data access | `var` (dotted path, escape-segments rejected), `missing`, `missing_some` |
| Bounds | `min`, `max` |

Explicitly **rejected** (standard JSON Logic ops not in v1.2): `map`, `reduce`, `filter`, `merge`, `cat`, `substr`, `log`, regex operators, date/time helpers, any custom or extension operator.

Escalation path: if a real predicate cannot be expressed inside this allowlist, restructure the issuer-side data shape OR escalate to a future v1.3 amendment proposing Rego/OPA. Custom operators are **never** added.

## 4. Verifier contract

A v1.2-compliant verifier MUST:

1. Treat v1.1 receipts (no `iat_ms`/`kind`/`cause`/`predicate`) as valid.
2. When `claim_type ∈ {ar.provenance.v1, ar.batch.v1}` and `predicate !== null/undefined`, reject with `predicate_forbidden_on_claim_type`.
3. When `iat_ms` is present, reject `iat_ms !== Date.parse(iat)` with `iat_ms_mismatch`.
4. When `predicate !== null/undefined`:
   - Static-validate the AST against the v1.2 allowlist + path policy (`predicate_operator_not_allowed`, `predicate_var_path_invalid`, `predicate_malformed_ast`).
   - Evaluate the AST against the canonicalised envelope as the input context. Require strict `true`. Any other result rejects with `predicate_evaluation_false`.
   - Division-by-zero and modulo-by-zero are explicit error codes (`predicate_division_by_zero`, `predicate_modulo_by_zero`), not implementation-defined (no NaN, no Infinity).
5. `kind` and `cause` are advisory — MAY surface in verification output for consumer filtering; no enforcement.

Status List revocation MUST NOT short-circuit predicate evaluation. A revoked receipt with a satisfied predicate surfaces as `signature: valid, predicate: satisfied, revoked: true (as_of: <T>)`.

A v1.2-compliant issuer MUST:

1. Set `iat_ms = Date.parse(iat)` exactly when minting under v1.2.
2. Set `kind` per the member-spec matrix (`null` on `ar.provenance.v1` and `ar.batch.v1`; `decision` on most others; `observation` on `ar.evaluation.v1`).
3. NEVER set `predicate` on `ar.provenance.v1` or `ar.batch.v1`.
4. If setting `predicate`, ensure it evaluates to `true` against the receipt at mint time. Issuing a predicate that evaluates to `false` is a protocol violation.
